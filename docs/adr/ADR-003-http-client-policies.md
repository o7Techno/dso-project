# ADR-003: Политики HTTP-клиента (таймауты, лимиты, ретраи)

- **Статус:** Принято
- **Дата:** 2025-11-03

## Контекст
Взаимодействие с внешними сервисами (например, календарь, почта) должно быть устойчивым и ограниченным по ресурсам. Отсутствие таймаутов и лимитов приводит к блокировке потоков и деградации системы.

## Рассмотренные альтернативы

### 🔹 Альтернатива A — без централизованных политик (таймауты в коде)
- **Плюсы:** быстро начать, гибко на уровне функций.
- **Минусы:** расхождение конфигураций, пропущенные таймауты.
- **Вывод:** отклонено.

### 🔹 Альтернатива B — сторонний прокси (Envoy, Istio)
- **Плюсы:** централизованный контроль, метрики, retrie-политики.
- **Минусы:** повышенная сложность и накладные расходы.
- **Вывод:** отложено до масштабирования.

### 🔹 Альтернатива C — встроенные политики клиента
- **Плюсы:** минимальная зависимость, прозрачность в коде.
- **Минусы:** требуется дисциплина при вызовах.
- **Вывод:** выбрано как оптимальное решение для текущего масштаба.

## Решение
- Таймауты: подключение ≤1 с, чтение ≤4 с, общий ≤5 с.
- Ретраи: ≤2 раз с backoff (100 мс, 200 мс).
- Лимиты на размер ответа, запрет бесконечных потоков.
- Конфигурация через переменные окружения; корреляция заголовка `x-correlation-id`.

## Влияние на безопасность
- Снижает DoS и утечки из-за зависших соединений.
- Уменьшает риск блокировок пула соединений.
- Побочный эффект: возможные кратковременные задержки при retrie.

## Меры смягчения
- Мониторинг latency и retry-count через метрики.
- Настройка алертов при превышении таймаутов.

## Definition of Done
- Все внешние HTTP-клиенты используют единый wrapper с таймаутами.
- Все юнит/интеграционные тесты проходят; SLO на latency соблюден.
- Настроены метрики retry/timeout в observability.

## Rollout-план
1. Включить политики в тестовом окружении.
2. Проверить нагрузочные сценарии с симуляцией таймаутов.
3. Включить на production, задокументировать переменные окружения.
4. Через неделю сверить метрики latency и количество retrie.
